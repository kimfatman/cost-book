## 二、计算科学性（严重，按优先级排序）

### C1【严重】"成本率"实为"毛利率"：核心指标口径错误
- `mock.js` 中 `products[].ratio` 的计算口径是 `(1 - cost / price) × 100`（`subpages.js` deleteBom / `api.js` addBomItem 同款），即**毛利率**。
- 但全产品把它当"成本率"展示：列表 `成本率 63.8%`、TOP5 `成本率 63.8%`、超支阈值 `>60 偏高 / ≥66 警示`、目标 `65%`。
- 同一数值在 `product-detail` 顶部环却标注**"毛利率"** → **同一字段两种标签，互相矛盾**。
- 实例：水煮鱼售价 ¥68、成本 ¥24.6，真实成本率 = 36.2%，页面却显示"成本率 63.8%"并接近警示线。
- 影响：商家会被严重误导（以为成本占售价 64%，实际仅 36%）；所有基于该值的超支判断、TOP5、目标对比均失真。
- 修复：统一口径为 `cost/price`（成本率）或明确改名为"毛利率"，并同步调整阈值与文案；`docs/03` 中的公式 `1 - cost/price` 一并更正。

### C2【严重】菜品 status（达标/超支）与页面展示的 ratio 自相矛盾
- 代码规则（`subpages.js` / `api.js`）：`ratio < 60 → 超支`。
- mock 数据：p3 回锅肉 `ratio=58.6` 却标"达标"；p6 担担面 `ratio=65.0` 却标"超支"——两条都与代码规则相反（若按真实成本率口径 41%/35% 则都该"达标"）。
- 影响：超支统计（`overCount`）、列表红绿、警示条全部可能指向错误菜品。
- 修复：以统一后的口径重算全部 status，并让 `addBomItem`/`deleteBom` 与列表判定共用同一函数。

### C3【严重】隐性成本"成本率漏损"恒为 0，且双重计算
- `hidden-cost.js` canteen 模型：`fullRatio = theoRatio + 30`，而 `theoCost` 已含 `labor + overhead`（= `p.cost`），`+30` 为重复计入。
- 演示数据下 `actualRatio(60.0%) - fullRatio(66.3%) - 2 < 0 → leak = 0`，该模块**永不报警**，与工作台"成本率 60.0% 偏高、环比 +1.8pp 提醒"的叙事直接矛盾。
- 若去掉 `+30`，漏损又飙到 ¥46,500（21.7% 营收）——因为**口径混用**：实际成本率是全口径（含房租/营销/折旧），理论成本率是产品级口径（仅食材+人工+水电分摊），两者差值主要是口径外成本，却被全部计为"漏损"。
- 修复：明确理论口径（全口径），或用"实际成本率 − 行业基准成本率"做区间判定，删除重复的 `+30`；同时在 UI 注明估算假设。

### C4【中】6 月成本率全链路不一致（58.2 vs 58.96）
- 实际计算：`116,980 ÷ 198,400 = 58.96%`。
- 但 `month.lastRatio = 58.2`、`periods.last.ratio = 58.2`、`reports R202606 ratio = 58.2` 全部写死 58.2。
- 连带影响：`ratioDelta = 60.0 − 58.2 = +1.8pp` 正确但建立在错误基线上（真实为 +1.07pp）；报表详情"环比"条、成本率对比全部偏差。
- 修复：以 `cost/revenue` 实测重算，或修正 mock 数据。

### C5【中】上月收入/毛利基数自相矛盾
- `month.prevRevenue = 201,800`，但 `trend[5月6月].revenue = 198,400`、`periods.last.revenue = 198,400`、报表 R202606 同为 198,400 → 收入环比 `+6.2%` 基数错误（按 198,400 实为 +8.0%）。
- `month.prevProfit = 81,260` vs 6 月毛利 81,420 → `profitDelta +5.4%` 基数错误（实为 +5.2%）。

### C6【中】报表分类"环比 delta"与占比差值对不上
- R202606 食材采购 `pct 48.1 / delta -0.6`，但 5 月 pct 47.2，实际差 +0.9；7 项中 5 项不符（R202605 亦有多处）。delta 为手填且未按 `pct 差值`校验。
- 修复：delta 应改为渲染时由相邻期 pct 实时计算，或加数据校验脚本。

### C7【中】TOP5 delta 与菜品历史环比不一致
- 水煮鱼 `topProducts.delta = -1.5`，但 `history` 末两位差 = -0.6；酸菜鱼 -0.4 vs -0.1；口水鸡 -0.5 vs -0.1（3/5 不符）。

### C8【低】BOM 用量金额 = 单价，数量/规格不参与计算
- `submitBom` 中 `amount = price`，`qty: '2 份'`、`spec` 均不参与金额；`deleteBom` 只减一项金额。演示简化可接受，但会造成 BOM 金额与真实用量脱节。
- 建议：`amount = price × qty数`（解析 qty 中的数字），或在 UI 标注"金额为单项金额"。

### C9【低】fresh 模型损耗率分母异常
- `lossAmt / (lossAmt + revenue)` 作"金额损耗率"，标准口径应为 损耗金额 ÷ 销售额（或进货额）。

### C10【低】健康度按金额加权
- 大金额项主导整体健康度，小金额高风险项被稀释。设计可接受，但应在 UI 注明加权方式。

## 四、功能易用性

### U1【中】登录页协议勾选框：视觉已勾选、逻辑未同意
- `#lgAgree` 初始渲染为蓝色底 + 白色对勾（视觉=已同意），但 `agreed = false`。用户直接点"登录/注册"会被提示"请先阅读并同意"，与所见不符。
- 修复：初始渲染为未勾选态，或默认 `agreed = true`。

### U2【中】日期"周几"标签整体错位一天
- `friendlyDate`：`'一二三四五六日'[new Date(d).getDay()]` — `getDay()=0` 是周日，该字符串索引 0 却是"一"。7/13（周一）会显示"周二"，全部日期错位一天（7/14 走"今天"分支不暴露）。
- 修复：改用 `'日一二三四五六'[getDay()]`。

### U3【中】删除/新增记录后全局数字不变（假联动）
- 删除一笔 ¥3,860 记录：列表消失，但工作台"本月总成本 ¥128,640"、分析构成、预算进度纹丝不动；保存新记录同理。
- 记一笔表单还写着"保存后自动归集到月度成本构成"——目前是**假功能**。
- 修复：`saveRecord/deleteRecord` 成功后同步重算 `month.cost / recordCount / share`（或明确标注演示期不联动）。

### U4【中】分析页"上月"切换不完整
- 切"上月"仅环形图换数据；趋势图标题硬编码"成本率 60.0%"、TOP5、供应商、隐性成本仍为本月数据，容易让用户误读为上月数据。

### U5【中】"成本率/毛利率"标签打架（与 C1 同源）
- 同数值在菜品列表标"成本率"、详情环标"毛利率"、顶部又挂"目标成本率 65%"标签，用户无法理解。

### U6【低】成本率 KPI 颜色语义混乱
- 工作台：收入/毛利上涨用红色（`--c-danger`），成本率上涨用灰色；涨跌方向与警示语义混用，建议：好指标上涨用品牌色、坏指标（成本率）上涨用警示色。

### U7【低】删除用料后的"超支"判定方向与直觉相反
- `deleteBom`：`ratio < 60 → 超支`（毛利率口径）。成本越高 → 毛利率越低 → 标"超支"，数值巧合自洽，但用户看到"成本率 63.8%"时完全无法对应。

### U8【低】健壮性：多处硬编码导致边界崩溃/溢出
- `renderShare` 假设 `share` 至少 7 项（`share[5]+share[6]`）；删除分类后可能越界或显示错。
- `renderAnaTop` 硬编码 `maxCost = 25`，新增高成本菜品条形溢出。
- `recordState.keyword` 直接内插 HTML（未走 esc），搜索词含 `"` 可破结构（本地演示低危）。
- 修复：动态取最大值、`esc()` 收口所有动态插值、share 长度防御。

### U9【低】演示性反馈未标注
- 凭证"拍照/相册"只生成假缩略图、报表"导出/分享"仅 toast、供应商"拨打电话"固定 `138****6622`——演示可接受，建议在 UI 增加"演示"角标避免误当真功能。

### U10【低】日期面板固定 2026-07 不可跨月
- 记一笔只能选 7 月内日期；作为演示限制可接受，但缺少"仅支持本月"的提示。

## 五、健壮性与代码质量

- **Q1** 架构分层、事件托管、`App.register` 生命周期、API 桩签名统一，属原型最优实践，docs 文档完备（01–08）。
- **Q2** `esc()` 未转义单引号与 `/`，当前属性均双引号包裹，低危；建议统一收口。
- **Q3** `App.ctx` 合并而非覆盖、Tab 去重、重复点击不入栈——交互层设计良好。
- **Q4** `sheet` 回调键名 `onClick` 与 `confirm` 的 `onOk` 不统一，易混（低）。
- **Q5** `getProducts` 返回的 `total` 是全集长度而非过滤后长度，语义模糊（未使用，低）。
- **Q6** 演示数据真实感强（供应商/菜品/记录互有关联），有助于走查，值得保留。
