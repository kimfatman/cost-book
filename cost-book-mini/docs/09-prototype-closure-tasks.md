# cost-book 原型收口阶段任务清单

**适用方案：** 双轨并行开发中的“原型质量收口”轨道  
**目标：** 在不重写现有视觉和路由骨架的前提下，使静态原型的数据口径统一、核心交互可回归、异常状态可解释，并为后续真实小程序迁移提供稳定的业务契约。

## 一、阶段目标与边界

当前项目的页面层、路由机制、API 桩和模拟数据已经形成完整演示骨架；原型收口阶段不负责直接实现微信登录、云数据库、云函数或真实文件存储，而是负责把这些未来能力所依赖的**业务规则、接口返回结构和验收口径先固定下来**。[1] [2]

本阶段的完成标准不是“每个页面都再改一遍”，而是让用户从登录演示入口开始，可以稳定走完工作台、记账、成本分析、菜品成本、供应商、分类和报表等主要路径；同一笔数据在列表、统计卡、图表和详情中不出现互相矛盾；任何失败、空数据或无权限场景都有明确反馈；后续迁移到真实后端时，页面不需要重新发明业务规则。

## 二、优先级说明

| 优先级 | 定义 | 处理原则 |
|---|---|---|
| P0 | 阻塞可信演示或会导致后端迁移返工的问题 | 第一迭代必须完成 |
| P1 | 影响核心体验完整性和回归效率的问题 | 第一迭代完成主体，必要时拆到第二迭代 |
| P2 | 提升专业度、可维护性和发布质量的问题 | 在 P0/P1 稳定后完成 |

## 三、P0：数据口径与核心规则收口

| 编号 | 任务 | 具体工作 | 依赖 | 验收标准 |
|---|---|---|---|---|
| P0-01 | 确定演示数据的“完整账本”口径 | 明确 `DB.records` 是完整月度明细，还是仅用于展示的精选子集；推荐在原型收口阶段统一为完整账本，避免明细合计与 KPI 脱节。同步更新 `README`、数据模型文档和页面文案。 | 无 | 文档明确记录口径；产品、记录、报表和分析页对“本月”的定义一致；不再出现用户无法解释的 `¥55,220` 明细支出与 `¥128,640` 月度成本并存情况。 |
| P0-02 | 修复月度记录计数 | 统一 `DB.month.recordCount` 与记录明细数量；新增、删除记录后同步更新；确认收入记录是否计入“本月笔数”。 | P0-01 | 初始数据计数正确；新增 1 条记录后加 1；删除该记录后恢复；刷新演示入口后结果可重复。 |
| P0-03 | 建立月度指标单一计算入口 | 抽取 `calculateMonthMetrics(records, period)` 或等价函数，集中计算支出、收入、毛利、成本率、预算使用率和记录数；页面不得各自拼装同一指标。 | P0-01 | 工作台、记账页统计条、分析页和报表详情使用同一计算结果；核心指标可通过一组固定测试数据复算。 |
| P0-04 | 统一成本率与产品状态规则 | 在共享业务函数或 API 层定义目标成本率、偏高、超支、警示的阈值和文案；修正 `担担面 65.0%` 与 `口水鸡 66.4%` 状态不一致问题；禁止 `api.js` 单独使用另一套 `ratio < 60` 规则。 | P0-03 | 同一产品在列表、详情、TOP5 和 BOM 重算后的状态一致；阈值边界值至少覆盖 59.9%、60.0%、65.0%、65.9%、66.0%、66.4% 和 70.0%。 |
| P0-05 | 固定金额、百分比和四舍五入规则 | 统一金额保留 2 位、展示金额保留 0/2 位的场景、成本率保留 1 位、占比合计的尾差处理和零金额处理。 | P0-03 | 所有金额展示无 `NaN`、`undefined` 或长小数；图表占比与明细显示的舍入差异有明确处理。 |
| P0-06 | 修复记录 ID 生成策略 | 取消以固定日期和数组长度拼接 ID 的脆弱策略，至少保证删除后新增、连续新增和跨日期新增不会产生重复 ID；为真实后端迁移保留可替换边界。 | P0-02 | 连续新增 100 条、删除中间记录后再次新增，ID 全部唯一且详情、删除、编辑仍能准确定位。 |

> **决策门：** P0-01 必须先确定。如果保留精选子集而不补齐记录，则必须在界面上显式标注“演示数据/聚合快照”，并禁止用户把列表合计理解为月度总账；更推荐补齐或重算 mock 数据，使演示默认口径自洽。

## 四、P0：核心业务流程收口

| 编号 | 任务 | 具体工作 | 依赖 | 验收标准 |
|---|---|---|---|---|
| P0-07 | 记账新增流程 | 完成支出/收入、金额、分类、日期、商户、备注和凭证状态的统一校验；保存后刷新列表和聚合指标。 | P0-02 至 P0-05 | 正常数据可保存；金额为空、为 0、为负数、含非法字符时均阻止提交并给出字段级提示；收入和支出符号、统计影响正确。 |
| P0-08 | 记账删除与详情流程 | 统一删除确认、详情展示、删除后返回和统计刷新；明确是否允许删除已核算记录。 | P0-02、P0-06 | 取消确认不会删除；确认后记录从列表消失、笔数和指标恢复；不存在的 ID 返回可解释错误。 |
| P0-09 | 菜品 BOM 增删改与重算 | 补齐 BOM 编辑、删除和新增后的成本重算；让 `bomTotal`、`cost`、`ratio`、`status` 经过统一函数更新，避免页面直接改 `DB`。 | P0-04、P0-05 | 新增、修改、删除一项用料后，BOM 合计、单位成本、毛利率和状态同步变化；取消操作不产生数据变化；异常金额不会写入。 |
| P0-10 | 分类占用校验 | 删除分类前检查记录、产品或其他引用；统一返回 `code` 和 `reason`，不让页面通过字符串猜测失败原因。 | P0-03 | 被记录或产品使用的分类不可删除，并显示具体原因；未使用分类可删除；删除后筛选器和表单选项同步刷新。 |
| P0-11 | 供应商 CRUD 收口 | 统一新增、编辑、删除、搜索、空列表和重复名称处理；补充联系人、电话等字段的基础校验。 | P0-05 | 新增供应商能在列表和分析页出现；编辑保留已有统计字段；删除需要二次确认；搜索结果与总数一致。 |
| P0-12 | 报表详情与导出交互定稿 | 明确当前“导出”是演示反馈还是生成真实 CSV/JSON 文件；原型阶段至少完成可重复的导出反馈和错误处理，不制造“已下载但没有文件”的假成功。 | P0-03、P0-05 | 用户能看到导出成功/失败结果；导出内容的月份、总成本、收入、毛利、成本率和分类明细与页面一致。 |

## 五、P1：API 桩层、状态和边界体验

| 编号 | 任务 | 具体工作 | 依赖 | 验收标准 |
|---|---|---|---|---|
| P1-01 | 统一 API 返回和错误处理 | 所有 API 统一 `{ code, data, message }` 约定；页面统一处理 `code !== 0`、异常、超时和空结果。 | P0-07 至 P0-12 | 任一接口失败都有可读提示；失败不会留下半更新状态；所有列表都有加载、空态和错误态。 |
| P1-02 | 补齐加载和防重复提交 | 检查工作台、记账、分析、菜品、报表、供应商和分类页面的骨架屏；保存/删除/导出期间禁用重复点击。 | P1-01 | 网络延迟期间页面有明确 loading；连续点击保存不会产生重复记录；操作完成后按钮恢复。 |
| P1-03 | 统一路由生命周期 | 检查 Tab 重复点击、子页返回、从子页返回后刷新、`App.ctx` 临时字段清理和事件解绑。 | 无 | 任一页面重复进入不会重复绑定事件；返回后列表数据是最新状态；浏览器控制台无明显报错。 |
| P1-04 | 完成登录演示和行业引导边界 | 明确“演示数据”“登录/注册”“行业模板”之间的状态关系；提供重置演示数据和重新进入引导的方式，避免 `localStorage` 让测试状态不可逆。 | P0-01 | 新用户、演示用户、完成引导用户三种状态均可重复体验；重置后回到确定的初始数据。 |
| P1-05 | 凭证交互一致性 | 保留模拟拍照/相册能力，但明确“模拟上传”状态；展示已添加、移除、取消和失败反馈，避免用户误认为文件已持久化。 | P1-01 | 添加和取消行为可重复；界面不宣称已上传真实文件；后续接云存储时有明确替换点。 |
| P1-06 | 隐性成本模型说明 | 明确模型版本、行业参数、估算性质和数据来源；统一健康度、等级和建议文案，避免把估算结果表述为财务事实。 | P0-03、P0-05 | 页面显示“估算/模型”提示；参数修改有集中入口；同一经营数据重复计算结果稳定。 |

## 六、P1：视觉与可用性回归

| 编号 | 任务 | 具体工作 | 依赖 | 验收标准 |
|---|---|---|---|---|
| P1-07 | 移动端尺寸回归 | 在窄屏、常见手机宽度和桌面居中预览下检查长列表、弹窗、底部 Tab、FAB、图表和表单。 | P1-03 | 无横向溢出；弹窗不被底部操作区遮挡；长文本和金额不破坏布局。 |
| P1-08 | 表单可访问性和输入体验 | 为输入项补充明确 label、错误提示和合理 input 类型；检查键盘弹出、数字输入、焦点顺序和取消操作。 | P0-07、P1-02 | 用户无需依赖 placeholder 才能理解字段；非法输入有定位提示；移动端键盘不会遮挡提交按钮。 |
| P1-09 | 空态、异常态和权限态文案 | 为无记录、无菜品、无供应商、分类不可删、接口失败和演示状态补齐真实业务文案。 | P1-01 | 每个空态都说明当前状态和下一步动作；不存在 lorem/sample 或含糊的“操作失败”。 |
| P1-10 | 图表与统计可解释性 | 为环形图、趋势柱状图和 TOP5 增加单位、时间范围、零值和无数据处理；检查颜色与分类映射一致。 | P0-03、P0-05 | 图表总和与明细一致；切换本月/上月后标题、金额和图表同步变化。 |

## 七、P1/P2：工程质量与可回归交付

| 编号 | 任务 | 具体工作 | 依赖 | 验收标准 |
|---|---|---|---|---|
| P1-11 | 建立无第三方依赖的单元测试 | 使用 Node 内置测试能力覆盖金额计算、成本率、状态阈值、记录计数、BOM 重算、分类占用和 ID 生成；不引入大型浏览器依赖。 | P0-03 至 P0-06 | 关键业务规则至少有正常值、边界值和失败值测试；测试可在干净环境一次运行。 |
| P1-12 | 建立静态语法和冒烟检查 | 将 `node --check`、测试执行、静态服务器 HTTP 200、关键资源存在性检查统一成脚本。 | P1-11 | 一条命令能完成静态检查；语法错误、测试失败或资源缺失时返回非 0。 |
| P1-13 | 增加 GitHub Actions CI | 增加轻量工作流，执行语法检查、单元测试和静态资源检查；不在 CI 中下载大型浏览器。 | P1-12 | 每次 push/PR 都能得到明确通过或失败结果；失败日志能定位到任务。 |
| P1-14 | 编写核心流程回归手册 | 将登录演示、记账新增/删除、分析切换、菜品 BOM、供应商 CRUD、分类删除、报表导出和重置数据写成固定步骤。 | P0-07 至 P1-10 | 新开发者按文档可以在本地重复完成验证；每次发布都有记录。 |
| P2-01 | 补充代码注释和模块边界 | 为共享规则、API 替换点、演示态持久化和直接读写 `DB` 的例外增加注释，清理过时说明。 | P0/P1 完成后 | 未来迁移云函数时能准确识别哪些逻辑必须下沉服务端。 |
| P2-02 | 更新版本和变更日志 | 将原型版本从当前 `v2.4.1` 更新为收口版本，记录数据口径、规则阈值、测试和已知限制。 | P1-12、P1-14 | README、维护手册和变更日志三处版本信息一致。 |
| P2-03 | 建立轻量发布流程 | 明确静态托管目录、发布前检查、回滚方式和演示数据重置方式；必要时添加 GitHub Release。 | P1-13、P2-02 | 新提交可以被复现发布；发布内容不包含临时测试数据或调试文件。 |

## 八、推荐实施顺序

### 迭代 1：先锁定规则和数据口径

先完成 P0-01 至 P0-06，尤其是演示数据完整账本口径、月度指标单一计算入口和成本率状态规则。这一批任务决定后续所有页面是否可信，也是双轨方案与真实小程序轨道共享的业务基础。完成后应形成一份简短的“成本核算规则”文档，作为未来云函数实现的输入。

### 迭代 2：收口核心 CRUD 和数据刷新

随后完成 P0-07 至 P0-12，重点验证新增/删除记录、BOM 重算、分类占用校验、供应商管理和报表导出。该迭代结束时，用户应能完整演示一条业务数据从录入到统计、分析和报表的流转。

### 迭代 3：补齐状态、交互和移动端体验

第三批完成 P1-01 至 P1-10，重点解决失败、空数据、loading、防重复提交、路由返回、移动端布局和估算结果说明。这一批任务会显著降低演示时的“偶发失效”与误解风险。

### 迭代 4：建立可持续交付能力

最后完成 P1-11 至 P2-03，形成不依赖人工记忆的检查、测试、CI 和发布流程。此时原型收口轨道可以稳定交付，双轨中的真实小程序轨道再安全地复用已经验证过的业务规则和接口契约。

## 九、与真实小程序轨道的协作边界

为了避免双轨并行时互相覆盖，建议使用两个分支：`feat/prototype-closure` 用于原型收口，`feat/wechat-foundation` 用于真实小程序基础设计。真实小程序轨道第一阶段只新增架构文档、数据迁移映射、云函数契约和环境说明，不直接重写原型的 `index.html`、`app.js`、`subpages.js` 或 `api.js`；这些共享文件应在 P0 规则完成后再通过明确的合并提交同步。

原型收口轨道需要向真实小程序轨道输出四类稳定成果：一是成本率和状态阈值；二是记录、月度指标、报表和 BOM 的数据模型；三是 API 返回和错误结构；四是固定的业务回归用例。真实小程序轨道则负责把这些规则落实到 WXML/WXSS/JS、云函数、云数据库和云存储中，而不是重新定义它们。[3]

## 十、阶段完成定义（Definition of Done）

原型收口阶段只有在以下条件全部满足时才算完成：

| 类别 | 完成条件 |
|---|---|
| 数据 | 月度指标、记录明细、成本构成和报表的口径有书面定义；关键合计和计数能通过自动检查；不存在已知的阈值矛盾 |
| 业务 | 记账、删除、BOM、供应商、分类和报表核心流程均有成功、失败和边界行为 |
| 交互 | 所有异步列表都有 loading/空态/错误态；保存、删除和导出不会重复提交；返回后数据会刷新 |
| 视觉 | 目标移动端宽度下无横向溢出；图表、弹窗、底部 Tab 和长列表可用；品牌令牌没有被新样式破坏 |
| 工程 | JavaScript 语法检查、业务规则测试、静态资源检查和冒烟路径均能一键执行 |
| 文档 | README、开发指南、数据模型、维护手册、回归手册和变更日志反映当前真实行为 |
| 双轨交付 | 已输出可供真实小程序复用的规则、数据模型、API 契约和回归用例；没有把临时演示逻辑误当成生产能力 |
